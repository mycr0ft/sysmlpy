# Endpoints and metadata applications — implementation plan (issues #23, #24)

Status: plan only, nothing implemented. Written 2026-10-30 against 0.99.7.

Source of the requirement: the CARTA team (SysML v2 → program-roadmap tool) uses
`sysmlpy.parse()` and the element object model as their parser. Two of their
eight findings need API work rather than a patch:

- **#23** relationships lose their endpoints (`dependency`, `allocate`,
  `satisfy`, `verify`)
- **#24** metadata applications are not exposed (`@M { … }`, `#M` prefix,
  `metadata … about`)

Their workarounds today are a ~300-line source-text scanner for traceability
and a separate scanner for metadata forms. The goal of this work is to delete
both.

---

## 1. What exists today (probed, not assumed)

Probes run against 0.99.7 with `load_grammar` (visitor dict), the grammar
classes, and `loads` (public model). "Visitor" = the dict `load_grammar`
returns; "grammar" = the `sysmlpy.grammar.classes` object stored on
`element.grammar`; "public" = the element object model.

| Construct | Visitor dict | Grammar object | Public model |
|---|---|---|---|
| `dependency d from A to B;` | `clients: [QualifiedName A]`, `suppliers: [QualifiedName B]` | `Dependency.clients/.suppliers` populated | `Dependency` element exists, `clients == []`, `suppliers == []` |
| `allocate a to b;` / `allocation al allocate a to b;` | `part` = ConnectorPart with both ends | `AllocationUsage.connectorPart` populated | `Allocation` element exists, no source/target |
| `satisfy R by S;` | `SatisfyRequirementUsage` with `ors`, `ssm` | `SatisfyRequirementUsage.ors/.ssm` populated | `Requirement` element with `keyword='requirement'`, `name=None`, `subject=None` — no requirement, no subject |
| `verification def V { objective { verify R; } }` | `VerifyRequirementUsage` (with `ors` → `R`) nested under `ObjectiveMember → ObjectiveRequirementUsage → RequirementBodyItem → RequirementVerificationMember` | not built | **no element at all** |
| `metadata m : M about X;` | `MetadataFeature` with `ownedRelationship_about: [Annotation(annotatedElement X)]`, `bodyFeatures: []` | `MetadataFeature.about/.bodyFeatures` | `Metadata` with `typed_by_name == 'M'`; no annotated element, no values |
| `part def X { @M { w = 1; } }` | `AnnotatingElement → MetadataFeature{type M, bodyFeatures[{name 'w', value '=1'}]}` at depth 18 | reachable via the body item | dropped for definition bodies; `X` carries nothing |
| `#M part def Y;` | **nothing emitted** (parse tree: `PartDefinition → OccurrenceDefinitionPrefix → DefinitionExtensionKeyword → PrefixMetadataMember`) | n/a | dropped at the visitor |

### What the dump does with these forms today

Also probed, because #24 cannot be "read-only": an annotation that does not
survive `dump()` is lost on the next save.

| Source | `dump()` output | Re-parses? | Verdict |
|---|---|---|---|
| `part def X { @M { a = 1; } @M { b = 2; } }` | `@ : M {a=1;};` ×2 | **no** — second parse yields `;` bodies | name slot printed as `:`, body unparseable; not idempotent |
| `@M { w = 1; }` at package level | `@ : M {w=1;};` | yes | stable but notation mangled (`@ : M`, no `@M`) |
| `metadata m : M about X;` | `@ m : M about X;;` | yes | keyword form lost, double terminator |
| `#M part def Y;` | `part def Y;` | yes | **prefix annotation lost entirely** |

So B2/B3 include serializer work, not just model API work, and every test needs
a dump → parse → dump fixed-point assertion.

Also probed and fine: `dependency d from A, B to C;`, `allocate (a, b, c);`,
`satisfy R;` (no `by`), `#M part y;` (usage form), `metadata m : M;` (no
`about`) all parse today, so the plan does not depend on grammar changes.

So: **only one construct needs visitor work** (`#M` prefix). Everything else has
the data already and loses it in the public model — that is the encouraging
part of this plan.

Relevant code anchors:

- `definition.py:1599` — `Dependency` branch builds `Dependency()` and never
  reads `inner_element.clients/.suppliers`.
- `usage.py:5395` — `Dependency` already has `clients` / `suppliers` fields.
- `usage.py:4719` — `Allocation` (no endpoint fields).
- `grammar/classes.py:10833` — `AllocationUsage.connectorPart` (present since
  issue #5 / PR #6).
- `grammar/classes.py:5569` — `SatisfyRequirementUsage.ors/.ssm` (traceability
  already reads them, which proves they survive).
- `antlr_visitor.py:9896-9977` — `VerifyRequirementUsage` dict builder (used
  for verification bodies, never reaches the public model).
- `definition.py:971` — `_add_metadata_child(mf)`: the single place a
  `MetadataFeature` becomes a `Metadata` element today; sets name and type only.
- `definition.py:1360-1390` — package-level `AnnotatingElement` /
  `NonOccurrenceUsageElement` branches (the `@`-form works at package level,
  not in definition bodies).

## 2. API to add

Design rules: names first, resolution opt-in (same philosophy as
`typed_by_name` / `model.resolve_types()`); no new required imports; every new
attribute is additive so 0.99.7 consumers keep working.

### #23 — endpoints

```python
dep.clients            # ['A']            names as written
dep.suppliers          # ['B']
dep.client_elements    # []  until model.resolve_references() (opt-in)
alloc.source / .target # ['a'] / ['b']   (lists: n-ary allocate is legal)
alloc.source_elements / .target_elements
sat.requirement        # 'R'       (name as written; None if anonymous form)
sat.satisfying         # ['S']     (the `by` subject; list — n-ary is legal)
sat.requirement_element / .satisfying_elements
verify.requirement     # 'R'
verify.requirement_element
case.verified_requirements        # on VerificationCase/VerificationDef: ['R']
```

`Dependency` also gains `dependency_elements` on the owner? No — keep it flat.

### #24 — metadata applications

```python
m.type_name            # 'M'        (alias of typed_by_name; exists)
m.annotated            # ['X']      `about` targets, names as written
m.annotated_elements   # [] until resolution
m.values               # {'w': 1}   bodyFeatures, typed where the syntax is a literal
m.value_text           # {'w': '=1'} raw text, for non-literals
x.annotations          # [Metadata, ...] every metadata applied to `x`
x.annotations_of('M')  # filter by type name
```

`x.annotations` is the piece that makes `@M { … }` and `#M` useful: an element
must be able to name what is attached to it, whichever notation applied it.

### Target script (this becomes `examples/metadata_and_endpoints.py`)

```python
m = loads(open("reproducer.sysml").read())
for el in m.all():                       # find/find_one/all exist today; no walk()
    for md in getattr(el, "annotations", []):
        print(el.name, "annotated by", md.type_name, md.values)
dep = m.find_one("d")
print(dep.clients, "->", dep.suppliers)
```

## 3. Work breakdown

### Phase A — #23 endpoints (release 0.100.0)

**A1. Dependency (S, ~2 h).** In `definition.py`'s `Dependency` branch, read
`inner_element.clients` / `.suppliers` (lists of `QualifiedName`) and pass the
joined names to `Dependency(clients=…, suppliers=…)`. Add `client_elements` /
`supplier_elements` resolving through the symbol table only when asked.
*Tests:* named + unnamed forms, multi-client (`dependency d from A, B to C;`),
round-trip unchanged.

**A2. Allocation (S, ~2 h).** Add `source` / `target` properties on
`Allocation` reading `self.grammar.connectorPart` (binary: 2 ends; n-ary: N
ends, `source` = first, `target` = rest). Same for `AllocationDefinition` if
the connector is accepted there (probe first — grammar allows
`allocationDefinition : occurrenceDefinitionPrefix ALLOCATION DEF definition`,
no connector).
*Tests:* `allocate a to b;`, `allocation al allocate a to b;`, n-ary
`allocate (a, b, c);`, dump round-trip (the connector already dumps).

**A3. Satisfy (S, ~3 h).** `Requirement` gains `requirement` /
`satisfying` reading `grammar.ors` / `grammar.ssm` (reuse the existing
`traceability._last_segment` style helper — move it to a shared place rather
than copy it). Populate `subject` (currently always None) from `ssm`.
*Tests:* `satisfy R by S;`, `satisfy R;` (no subject), qualified reference
`satisfy P::R by S;`, nested inside a requirement body.

**A4. Verify (M, ~6 h).** Two parts:
1. **Build the element.** The dict exists
   (`RequirementVerificationMember → VerifyRequirementUsage`); the requirement
   *body* walk that would reach it does not exist for verification cases.
   Add a `Verify` element (sysml_type `verify`) built from
   `VerifyRequirementUsage`, and make `RequirementBodyItem →
   RequirementVerificationMember` reachable from the body dispatch used by
   definitions.
2. **Expose it on the case.** `VerificationCase.verified_requirements`
   (names) from its own grammar body, so a consumer does not have to walk to
   find the Verify element.
   Also feeds `traceability.verified_by` (currently always empty — #27 item 3).
*Tests:* objective-verify, direct `verify R;` in a verification body, assert on
`VerificationCase.verified_requirements`, `traceability.verified_by`, and that
`dump()` still round-trips.

**A5. Interchange + docs (S, ~2 h).** New attributes are derived (not stored),
so `to_interchange` should be unaffected — verify with a round-trip test that
asserts the graph is byte-identical to 0.99.7's for a model using these
constructs. Add a README section + `examples/` script.

Phase A total: **~1.5 days** including tests, docs, release.

### Phase B — #24 metadata applications (release 0.101.0)

**B1. `Metadata` values and `about` (S, ~3 h).** Extend
`_add_metadata_child` (and the `Metadata` class) to read
`grammar.ownedRelationship_about` (→ `annotated` names) and
`grammar.bodyFeatures` (→ `values` / `value_text`; `bodyFeatures` already carry
`name`, `value`, `text`, `featureKeyword` from the PR #9 work). This alone
covers `metadata m : M about X;` for CARTA's planning-attribute use case.
*Tests:* about with one and several targets, values of literal and expression
form, `metadata m : M;` (no about).

**B2. `@M { … }` in every body + its serializer (M, ~7 h).** The visitor emits
`AnnotatingElement → MetadataFeature` inside definition bodies; the
definition-body dispatch drops it. Add the `AnnotatingElement` /
`NonOccurrenceUsageElement`-with-`MetadataFeature` handling the package loader
already has, attach the resulting `Metadata` to the **owning element** rather
than the enclosing namespace, and give every element an `annotations` list
(cheap: `[]` on the base class, appended to). **Plus the serializer**, without
which the model cannot be saved: `@M { a = 1; }` currently dumps as
`@ : M {a=1;};` (no name slot, not re-parseable inside a body) — the
`AnnotatingElement`/`MetadataFeature` dump needs the `@`-form without the
spurious `:` and a body that round-trips.
*Tests:* annotation on a part def, on an attribute, on a usage, two
annotations of the same type (the currently non-idempotent case), annotation
with a nested metadata body, each with dump → parse → dump.

**B3. `#M` prefix form + its serializer (M, ~8 h, the only visitor work).**
Capture `PrefixMetadataMember` where a definition/usage prefix is parsed
(`_get_occurrence_definition_prefix`, `_get_usage_prefix_dict` — both are
duplicated helpers, see the skill note) and carry it into the element dict as
`prefixMetadata`, then attach it as an annotation like B2. On the way out the
prefix must be emitted again — today `#M part def Y;` dumps as `part def Y;`,
losing the annotation.
*Tests:* `#M part def Y;`, `#M part y;`, prefixed usage with a name
(`#M part def Y { }`), two prefix annotations, and that the prefix survives
`dump()`.

**B4. Resolution + interchange + docs (S, ~4 h).** `annotated_elements`,
`model.resolve_references()` opt-in pass; decide whether annotations appear in
`to_interchange` output (they do not today; adding them changes graph shape —
see Risks); README + examples.

Phase B total: **~3 days** including tests, docs, release.

downstream deadline forces a split: **A1+A2+A3+B1 first** (≈1 day) removes
most of CARTA's text scanning, because those are the four edges they read most.

## 4. Risks and decisions

1. **Names vs elements.** The plan exposes names-as-written by default and
   resolved elements only on request. That keeps parsing cheap and avoids
   pretending a name resolved when it did not (`satisfy Reqs::R` where `Reqs`
   is a library package). *Decision needed:* do we want a single
   `model.resolve_references()` pass, or per-element properties that resolve
   lazily? Lazy is simpler to ship; a pass is easier to reason about.
2. **`verify` shape.** A `Verify` element in the tree changes child lists for
   verification cases — anyone diffing `children` sees new members. The
   alternative is a property only. *Decision needed:* element + property (this
   plan) or property only.
3. **`annotations` on the base class.** Every element gains an empty list, so
   `repr`/`dump` output must not change. Interchange is the risk: if
   annotations are exported, `@graph` shapes change for models that use them
   (new nodes are fine; new *properties* on existing nodes are a schema
   change). *Proposal:* annotations stay out of interchange in 0.101.0 and get
   their own increment with a version bump of the interchange format.
4. **Duplicate prefix helpers.** `_get_occurrence_usage_prefix` and
   `_get_usage_prefix_dict` are separate, already-diverged implementations.
   B3 must touch both (the skill records this exact family of bug).
5. **`bodyFeatures` values.** They carry text (`'=1'`), not typed literals.
   Typed extraction needs the expression layer; ship text first, add typed
   values only where the existing evaluator already handles the shape.
6. **Conformance check.** Every new API should be cross-checked against
   OpenSysML's validator for at least one positive and one negative model per
   construct — its error messages also tell us what it *requires*
   (e.g. it insists a connection usage carries its own ends).

## 5. Acceptance criteria

- The CARTA reproducers for #23 and #24 (as filed) produce no text scanning:
  endpoints and annotations readable from the object model alone.
- `dump()` → `parse()` → `dump()` stays a fixed point for every model in the
  new tests.
- `to_interchange` / `from_interchange` round-trip unchanged for a model that
  contains all four relationship forms and all three metadata forms.
- The ci gate on the bundled library does not regress (baseline at 0.99.7:
  0 parse failures, `DUPLICATE_NAME` 0, 2079 `UNDEFINED_SYMBOL`, 5643
  `UNRESOLVED_EXPRESSION_IDENTIFIER`, 577 `IMPLICIT_LIBRARY_IMPORT`).
- Full suite green; new tests named `tests/issue23_*_test.py` /
  `tests/issue24_*_test.py` per construct, plus one end-to-end
  `examples/metadata_and_endpoints.py`.

## 6. What is explicitly NOT in scope

- `interface` endpoints and `flow` payload feature values beyond names (flows
  now reach the model as of 0.99.7; their ends are readable from the grammar,
  exposing them is a separate small increment).
- Metadata *semantics* (evaluating metadata expressions, type checking
  against the metadata def's features). Values stay textual.
- The `dependency` grammar ambiguity recorded in `Dependency.dump` (unnamed
  `dependency name a to X;` is unparseable) — separate upstream question.
